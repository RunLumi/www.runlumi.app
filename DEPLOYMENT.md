# Deployment & operations

How this site reaches production, what each layer does, and how to diagnose
the failure modes we have already hit. For app-level setup (D1, R2, local
development) see [README](./README.md); for repo conventions see
[AGENTS.md](./AGENTS.md) and [DESIGN.md](./DESIGN.md).

## Production architecture

```
GitHub (main)
   │  git push
   ▼
ECC pre-push hook (local)          .git/hooks — blocks the push if any fail
   lint → typecheck → test → build
   ▼
GitHub Actions CI (.github/workflows/ci.yml)
   npm ci → lint → test → db:migrate:local → build
   ▼
Deploy (manual): npm run deploy
   preflight → astro check + build → wrangler deploy
   ▼
Cloudflare Worker "runlumi"
   routes: runlumi.app/* · www.runlumi.app/* (primary)
           landing.runlumi.app/* (compatibility alias)
   bindings: D1 (lumi-jobs · lumi-content) · R2 (lumi-job-files · lumi-blog-media) · SESSION KV · ASSETS
   secrets: EMDASH_ENCRYPTION_KEY · DISCORD_APPLICATION_WEBHOOK_URL · CRM_INTAKE_SECRET
   ▼
https://runlumi.app · https://www.runlumi.app
   /            prerendered landing pages
   /jobs        Astro SSR ← D1
   /admin/jobs* Astro SSR, EmDash-admin-gated ← D1/R2
   /crm · /vi/crm Astro SSR, EmDash-session and CRM-membership-gated ← lumi-jobs D1
   /api/intake/local  HMAC-signed server-to-server intake from local.runlumi.app
```

Key point: **there is no Cloudflare Pages deployment anymore.** A legacy
Pages project (`landing-runlumi-app`) existed earlier and served an old
static build from this repo's GitHub integration; its builds are disabled
(`deployments_enabled: false`) and it owns no domains. The Worker is the
only deployment path.

## Routing: why a zone route and not a custom domain

`wrangler.jsonc` attaches the Worker to production with:

```jsonc
"routes": [
  { "pattern": "runlumi.app/*", "zone_name": "runlumi.app" },
  { "pattern": "www.runlumi.app/*", "zone_name": "runlumi.app" },
  { "pattern": "landing.runlumi.app/*", "zone_name": "runlumi.app" }
]
```

A Worker **custom domain** (`"custom_domain": true`) cannot attach to a
hostname that already has DNS records — Cloudflare rejects it with error
`100117: Hostname already has externally managed DNS records`. The
The hostname records predate the Worker (they used to point at the Pages
project), and the wrangler OAuth session does not have
DNS-edit permission to delete them. A **zone route** is the correct tool:
it takes over an already-proxied hostname without touching DNS. Do not
switch back to `custom_domain` unless the DNS records are deleted first.

## Deployment

```bash
npm run deploy
```

Sequence: preflight → `astro check` + `astro build` → `wrangler deploy`.

- **Preflight** (`scripts/preflight.mjs`) checks that
  `EMDASH_ENCRYPTION_KEY`, `DISCORD_APPLICATION_WEBHOOK_URL` and
  `CRM_INTAKE_SECRET` exist. The CRM intake secret is shared with the
  `lumi-local` Pages project; see [docs/crm/RUNBOOK.md](docs/crm/RUNBOOK.md).
  EmDash owns admin sign-in and the session cookie; the app stores no admin
  password or second session secret.
- The Worker entry point is generated by `@astrojs/cloudflare`; static
  assets ship together with the Worker bundle.

Secrets are **only** stored via Cloudflare, never in the repo:

```bash
printf '%s' '<value>' | ./node_modules/.bin/wrangler secret put EMDASH_ENCRYPTION_KEY
printf '%s' '<value>' | ./node_modules/.bin/wrangler secret put DISCORD_APPLICATION_WEBHOOK_URL
```

Pipe from stdin (or run `wrangler secret put` interactively). Never pass
secret values as shell arguments — shell history and process lists leak,
and unquoted `$` in a double-quoted string is silently expanded by the
shell (this exact mistake once created junk secrets named after a
password; see incident history). Rotating either secret takes effect on
the next request; no redeploy is needed.

## Checks that gate every push

| Script           | What it runs                                          |
| ---------------- | ----------------------------------------------------- |
| `npm run lint`   | AGENTS.md policy linter (hype copy, remote deps, D1 blobs, locale peers) |
| `npm run typecheck` | `astro check`                                      |
| `npm run test`   | Node built-in runner over `src/lib` (26 tests)        |
| `npm run build`  | `astro check && astro build`                          |

The local ECC pre-push hook runs all four; CI runs the same set with
`npm ci` plus a local D1 migration. CI never uses `npm install` — see the
"Dependency install policy" in the README for the npm freshness-window
rationale.

## Incident history (what broke and why)

Worth reading before debugging: most of these failure modes look like
mysterious build or 404 errors but have precise causes.

1. **`Cannot find module '@astrojs/cloudflare'` during build.** The npm
   wrapper on Lumi machines injects a 7-day release-age filter
   (`--before`) into every install; two dependencies were newer than the
   window and the committed lockfile predated the adapter, so resolution
   failed. Fix: regenerated the lockfile with an explicit fresh window;
   permanent guard: `npm ci` everywhere (see README install policy).

2. **Pre-push build failed with the same missing-module error.** Same
   root cause; the fix shipped as a regenerated, committed
   `package-lock.json` that `npm ci` pins to.

3. **First deploy failed: D1 `database_id` was a placeholder.** The
   config shipped with an all-zero UUID and the `lumi-jobs` database did
   not exist. Fix: `wrangler d1 create lumi-jobs`, real ID in
   `wrangler.jsonc`, migrations applied remotely.

4. **Custom-domain attach rejected (error 100117).** Existing DNS
   records for `landing.runlumi.app` blocked the Worker custom domain.
   Fix: switched to a zone route (see Routing above). A stale Pages
   custom-domain association on the same hostname was removed via the
   Pages API first.

5. **`landing.runlumi.app/jobs` 404 while `runlumi.app/jobs` worked.**
   The hostname was still served by the legacy Pages project's static
   build, not the Worker. Fix: zone route + disabling the Pages
   integration. Diagnosis pattern: when a path works on one hostname and
   not another, check which service owns the hostname before touching
   app code.

6. **Legacy admin login rejected every password.** The former flow required
   `ADMIN_PASSWORD` and `ADMIN_SESSION_SECRET`. It was replaced with EmDash
   user sessions; the current user's active status and role define access.


7. **Junk secrets with password-like names in `wrangler secret list`.**
   A secret value containing `$` was passed through a shell in double
   quotes; the shell expanded it and the mangled fragments became secret
   names. Fix: junk secrets deleted; policy: stdin piping only (see
   Secrets above), and rotate any value that has been through a shell.

## Troubleshooting playbook

**A route returns 404 on production but works locally.**
Identify what serves the hostname before reading app code:
`dig` the hostname, then `curl -sI` and compare against the Worker URL.
Check the active route with `wrangler deploy --dry-run` output or the
Cloudflare dashboard (Workers → runlumi → Settings → Domains & Routes).

**A route returns 404 on both hostnames.**
Check whether the Worker is deployed at all
(`wrangler deployments list`) and whether the build output in `dist/`
actually contains the page (prerendered pages land in `dist/client`,
SSR routes only exist in the server bundle).

**Deploy fails at the trigger/hostname step.**
If it mentions error `100117`, a `custom_domain` was reintroduced — go
back to the zone route. If it mentions missing permissions, the wrangler
OAuth session expired or was refreshed with a narrower scope; rerun
`wrangler login`.

**Admin sign-in returns to the login page.**
Sign in at `/_emdash/admin/login` first. An authenticated account that
gets 403 at `/workspace/users` must be active and have the
EmDash admin role. Everyone else needs an enabled `workspace_members` entry
with the right role (HR for hiring, a sales role for the CRM); an admin grants
it from `/workspace/users` after the person has signed in once.

**Preflight fails naming a missing secret.**
Set it via stdin (commands above). If you must confirm which value is
correct, remember secret values are unreadable after being set — rotate
instead of trying to recover.

**CI red on a push that passed locally.**
CI runs `npm ci` from the committed lockfile; if you added a dependency
without committing the lockfile, or the lockfile and `package.json` have
drifted, CI fails where your machine (with `npm install`) passed. Commit
the regenerated lockfile.

**Build fails on freshly published packages again.**
Do not bypass the wrapper casually. Use the escape hatches from the
README: `PKG_MIN_AGE_DAYS=0 npm install <pkg>` for deliberate fresh
resolution, then commit the lockfile so everyone else gets `npm ci`
stability.

## Quick reference

```bash
npm run deploy                  # preflight + build + wrangler deploy
node scripts/preflight.mjs     # check required secrets exist
./node_modules/.bin/wrangler secret list
./node_modules/.bin/wrangler deployments list
./node_modules/.bin/wrangler d1 migrations apply lumi-jobs --remote  # = npm run db:migrate
./node_modules/.bin/wrangler tail runlumi   # live Worker logs
```

Remember: `npx` is blocked on dev machines without `--no-install` — use
package scripts or `./node_modules/.bin/<tool>` (README explains why).
