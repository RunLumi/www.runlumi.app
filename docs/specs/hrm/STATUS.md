## Implemented local scope

- Migration `0014_hrm_records.sql` adds HRM role grants and structured people, employment periods, profile/history, change-request, private-file, idempotency and audit tables without removing old role grants.
- Workspace roles remain separate for Employee, People Manager, HRM Officer and HRM Admin; System Super Admin remains EmDash role 50. HR/Finance/Sales/Partner do not gain HRM access through their old roles. Users and grants are still managed through the shared EmDash/Workspace contract.
- HR creates a record by selecting one active EmDash account; it does not auto-link by matching email. A person can have separate employment periods.
- HRM Admin can close an employment period and start a later rehire period on the same person record. A rehire preserves the prior period, checks the previous revision and new start date, requires the linked EmDash account to remain active, validates the manager, and is idempotent. It does not automatically restore revoked Workspace grants.
- Middleware rechecks linked employment on private HRM requests; when all employment periods have ended, the person loses every HRM route even if other HRM/manager roles remain. Workspace access in other modules is unchanged until System Super Admin disables the shared membership through the audited offboarding task.
- Employee self-service and scoped HR/manager views cover contact, personal, identity/CCCD, dependents, bank and tax/insurance fields. Riskier changes enter a versioned reviewer workflow; stale updates conflict. Actor, server time and audit history are retained.
- HRM file endpoints use private R2 objects under the `hrm/` namespace, signature-checked PDF/JPEG/PNG, a 5 MB cap, quarantine/review and authenticated no-store downloads. HR review is not an antivirus-scan claim.
- HRM is guarded by `HRM_LIVE_ENABLED` and reviewed settings. The production switch remains off.
- HRM page POST forms retain a bounded same-origin URL-encoded request clone before adapter consumption; oversized forms are rejected. Profile routes return mutation Responses instead of rendering them as page data.
- P2 legal slice is implemented in the local working tree: authorized HRM users upload bounded DOCX sources; another reviewer approves source files and versions; integration proves HRM Admin activates a contract version and System Super Admin activates a separately reviewed policy version; audience status is checked before issue; issue snapshots retain source checksum/version; employees can acknowledge the exact issued policy and the server stores actor/time/checksum immutably; employees and HR can upload quarantined PDF evidence to paper-signing issues; another reviewer records each required paper-signing party and server timestamp. No electronic-signature provider is configured.
- COI self-service and review pages now use EmDash identity and HRM-specific scope. Drafts capture both conflict/no-conflict declarations; assigned HRM Officer or Admin can request clarification, clear, require mitigation, escalate or close with actor/time/reason. PDF evidence is quarantined, scoped to the declaration and reviewer assignment, and cannot be self-reviewed. Amendments link to immutable prior submissions, snapshot the source revision and atomically mark the source superseded only when the new declaration is submitted. Stale source changes conflict; an unsubmitted draft can refresh its snapshot after reload/review.
- Onboarding templates are versioned and reviewed before activation; plans snapshot the selected version and applicability for one employment period. Todo supports owners/reviewers, cycle-checked dependencies, calendar-day due dates, previewed rescheduling, evidence submissions, independent review, authorized waivers, blocking, reassignment, cancellation and audit history. Employee, assigned manager/buddy and HR views are scoped; private records do not inherit onboarding visibility. Focused Worker/D1/R2 integration passed these flows.
- ATS transfer requires both `hiring.applications.manage` and `hrm.records.manage`, a hired application, a fresh preview of application/job/settings revisions, and manual selection of an active EmDash member with the Employee role. It creates the HRM person and preboarding period in one D1 command, transfers only name/contact/work fields, excludes CV/files/answers/notes/interviews/scorecards, stores an immutable non-cascading source reference and is idempotent. A synthetic source-application deletion test proves the HRM person and transfer record remain.
- Ending an employment period with an end date creates an offboarding case and checklist for handover, assets, Workspace access, records review and payroll closeout. HRM access is denied immediately to the linked ended person even if other HRM roles remain. Only System Super Admin can disable shared Workspace membership through the common audit/token-revocation path; role records remain for audited restoration. Starting a later employment period supersedes the prior open offboarding case instead of revoking a returning employee. The offboarding payroll-closeout task remains blocked until approved payroll rules and verified final reconciliation are linked; merged P4 code with production disabled does not mark it complete.
- Migration `0019_hrm_retention_controls.sql` adds versioned rules for every HRM file category with no seeded duration, legal holds by person/category or exact file, and append-only deletion requests. Only a separately reviewed active policy with an explicit duration makes a file eligible; `null` leaves it without an automatic due date. Holds apply to future uploads and block pending/approved requests. Release requires a different actor. File deletion requires an independent reviewer and a different System Super Admin executor; R2 deletion is retryable and leaves an immutable metadata/checksum tombstone. Switching policy versions retires the prior version and blocks pending approvals under it; an in-progress deletion must finish/recover first. Production activation and the category periods themselves remain unapproved.
- Retention policy versions now cover thirteen file categories, including `leave_evidence`, `service_evidence` and `training_evidence`, with no seeded durations. `retention_days:null` means no scheduled eligibility; the basis is captured per category and each version needs a different reviewer before activation. Person/category and exact-file holds are immutable, audited records; held status propagates to existing files and new uploads. A file request needs an active dated policy, a reviewed file, no hold, a separate reviewer and final System Super Admin executor. R2 deletion is retryable and marks a tombstone; metadata/checksum/audit remain. Policy rollover retires the old policy and blocks requests awaiting review/approval under that version.
- P3 migration `0020_hrm_time_leave.sql` adds schedules, attendance, locked-period snapshots, leave ledger and bounded CSV batches. Migration `0021_hrm_leave_evidence.sql` adds the `leave_evidence` private-file kind, request/file link and retention category without seeding a duration; migration `0022_hrm_leave_request_revisions.sql` adds immutable amendment snapshots and ties each evidence link to a semantic request revision. Required-evidence leave submissions remain pending until an independent file review; request approval blocks on missing/quarantined/stale-revision evidence. Amendment recalculates minutes against the current schedule/balance, records old/new snapshot plus actor/reason/time, retries idempotently, and requires a replacement PDF if evidence belonged to the prior revision. Migration `0023_hrm_approval_delegations.sql` adds dated time/leave substitutes, append-only history and revoke audit. Good returns become available; damaged items enter inspection; missing items are marked lost. Every transition is version-guarded and idempotent; no payroll deduction or outside provisioning is triggered. Concurrent/duplicate enrollment is blocked, same-key retries are idempotent, plan rollover retires the old version and waits for pending enrollment decisions.
